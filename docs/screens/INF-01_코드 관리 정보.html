length(판형)의 의미
  • length는 코드를 입힐 수 있는 최대 크기(판형)를 나타냅니다. (length ≒ 판형 크기)
  • 신규 프로젝트 시작 시 향후 발매 예정 콘텐츠의 판형까지 고려해 큰 사이즈가 필요하면, 그에 맞는 섹션·오너를 발행해 드립니다.
  • 초반에 작은 판형만 쓰다가 이후 큰 판형 교구에 코드 적용이 필요해지면, 신규 섹션의 코드를 발행해 펌웨어 혹은 서비스 프로그램에 추가하여 작업합니다.
  • 따라서 최대 적용 크기(판형=length)와 페이지 수를 모두 고려해야 하며, 판형 크기에 따라 섹션이 달라집니다.
※ Section 1은 테스트/개발 전용(상용 미출시).
※ Section 44 = PDS4(S-code) — owner 0~4095 · bookcode 0~255 · page 0~255 · xy 0~255 로 관리합니다 PC-042. PDS4 는 판형(length) 대신 xy 값을 가지므로 표의 마지막 행이 xy 입니다.

코드 종류 — 좌표(SOBP)의 속성

좌표(SOBP)가 먼저입니다. Section·Owner·Book·Page 로 코드를 지정하고, 그 좌표가 어떤 체계인지를 코드 종류로 구분합니다. 좌표는 유일하므로 코드 중복은 성립하지 않고, 해당 좌표가 PDS2·PDS3·PDS4·OID 중 무엇인지만 가리면 됩니다.

표기약칭설명
PDS3 (N3C6)NcodeN3C6의 N을 따서 Ncode. 현행 주력 코드.
PDS2 (G3C6)GcodeG3C6의 G를 따서 Gcode. 구형/호환 코드.
PDS4 (S-code)ScodeSection 44 로 발급된 좌표를 PDS4(S-code)로 구분합니다.
OID인덱스index만 갖는 코드 — 외부 코드를 우리 펜으로 읽을 목적으로 만든 방식. 옛 IDS(A코드) 표기도 같은 것으로 본다.
같은 S/O 는 PDS2·PDS3·PDS4 중 한 종류만 씁니다(무겹침). OID는 index 부여라 같은 S/O 를 함께 쓸 수 있습니다.
펜 구분(소리펜 NSP · 필기펜 NWP)도 좌표 속성이며 지도·목록에서 필터로 가릅니다.
SOBP 맵·코드 프로젝트에서 PDS2 · PDS3 · PDS4 · OID 로 필터해 조회합니다.
OID — index 전용 코드
개념 — OID는 index만 갖는 코드로, 외부 코드를 우리 펜으로 읽을 목적으로 만든 방식입니다.
OID 책을 우리 펜으로 찍으면 코드 값이 1개만 나옵니다.
총량이 약 60,000개뿐이라, 책의 양이 많지 않으면 book 으로 코드를 나누지 않습니다.
대장 관리 방식내용예
업체 구분S/O 로 업체를 구분해 왔습니다(관리 편의를 위한 구분이며 좌표 발급이 아닙니다).한솔 S3/O25 · 웅진 S3/O17
book 미분할분량이 6만 페이지 미만이면 book 번호로 나누지 않고 업체 단위로만 관리합니다.한솔교육 · 잉글리시에그 · 헤르만헤세 등
index 관리분량이 늘어난 업체는 book 번호로 나누며, 그 번호가 곧 OID index 로 보입니다.웅진 B431~464
조회 화면좌표 기준은 SOBP 맵의 종류 필터 [OID], OID 설명은 [티켓 정보] 탭의 OID 안내 카드에 있습니다(옛 [OID 관리대장] 탭은 폐지 PC-325).index 로만 관리 · 새로 발급하지 않음
용어옛 IDS(A코드) 표기는 OID 와 같은 것입니다. 화면·필터에서 구분하지 않습니다.IDS = OID

계정 — App Key와 한 묶음으로 관리되는 로그인 정보입니다. 항목: 회사정보 · ID(EMAIL) · PWD · NAME · ADDR · HOMEPAGE. 고객사 관리의 정보를 불러와 등록하며, App Key는 계정 없이 발급되지 않습니다(발급 화면에서 계정 등록 → App Key 발급이 한 흐름).
※ 비밀번호를 요청하지 않는 고객사(SDK 목적)는 담당자가 임의 비밀번호를 지정해 계정을 만들고, 그 id/pwd + SOBP가 포함된 App Key를 전달합니다.
⚠ Section 1은 테스트/개발 전용으로 만들어졌고 상용 서비스로는 미출시된 코드입니다(레거시 아님). Section 44는 PDS4(S-code) 로 구분합니다.

티켓 여러 개계정에 붙는다 · SOBP 가 바뀌면 티켓을 더 발급
  • App Key 는 고객사의 계정마다 1개만 만들어진다 — 계정을 만들 때 자동으로 생긴다.
  • 티켓은 App Key 에 매칭되지 않고 계정에 매칭된다 — 한 계정에 티켓(Code Type · Section · Owner · Book · Page · Info · Period)을 여러 개 발급할 수 있다.
  • 그래서 쓰는 코드(SOBP)가 늘거나 바뀌어도 App Key 는 그대로 두고 그 계정에 티켓만 더 발급한다. 정산도 티켓마다 한다.
  • 이전 정책으로 App Key 가 2개 만들어진 옛 계정은 기록대로 둘 다 보이지만, 새 키는 만들지 않는다.

OID — index 전용 코드 · 새로 발급하지 않음
  • OID = index 만 갖는 코드 — 외부 코드를 우리 펜으로 읽으려고 만든 방식입니다. OID 책을 우리 펜으로 찍으면 코드 값이 1개만 나옵니다. (옛 IDS 표기도 같은 것입니다)
  • 총량이 약 60,000개뿐이라, 책의 양이 많지 않으면 book 으로 코드를 나누지 않습니다. 업체 구분에는 S/O 를 써 왔고, 분량이 늘어난 업체만 book 번호(=OID index) 로 나눠 관리했습니다.
  • SOBP(PDS2·PDS3·PDS4) 좌표 관리와 달리 index 로만 관리합니다. 좌표로 보려면 SOBP 맵에서 종류 [OID] 로 필터하세요.
  • OID 는 티켓을 새로 발급하지 않는 코드 종류입니다(위 N Key 표 참고). 이력만 남아 있습니다.
세 티켓 공통
  • 고객사에 할당된 SOBP 안에서만 발급 · 지정합니다.
  • App Key · N Key · 서비스 티켓은 SOBP 가 겹칠 수 없습니다 — 고객사를 가리지 않고 전체 발급분과 비교합니다.
  • 발급한 티켓은 지우지 않고 고칩니다([티켓 수정]).
  • SOBP 할당에는 기간이 없고(한 번 할당받은 고객사가 영구 소유), 사용기간은 티켓에만 있습니다.

  • 그러나 이제 사업부·재무팀이 코드 발급 현황을 조회합니다 → "코드가 얼마나 발급되었는지" 확인 용도로 발급 규모를 봅니다.
