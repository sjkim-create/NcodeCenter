## 용어 기준

- **코드 좌표 = SOBP** (Section–Owner–Book–Page).
- **코드 종류 = N코드 / G코드** (참고: 물리 체계 PDS3≈N코드, PDS2≈G코드). **S코드는 NcodeCenter 범위에서 제외**(결정 2026-07-15).
- **펜 구분 데이터 = Ncp(소리펜) / Ndp(필기펜)** — 동일 page(동일 SOBP)라도 Ncp/Ndp로 **다르게 관리**.

## 1. 연속 페이지 부족 시 분리 정책 (확인1)

**정정**: (기존) 연속 부족 → *page 분리*(같은 book의 떨어진 페이지 사용) → **(정정) 연속 부족 → book 분리, 각 book 내 page 연속성 유지**. 같은 book의 떨어진 두 빈 구간을 **합쳐 쓰지 않는다**.

**적용 원칙**
- **무겹침(최우선)**: 신규 할당은 기존 할당과 **절대 겹치지 않는다.**
- **SO 원칙 유지**: 소유권(Section–Owner)에 따라 할당하면 다른 업체/프로젝트와 코드가 겹치지 않는다.
- **페이지 연속성 요건은 대상 애플리케이션에 따라 분기**:
  - **CasterN**: 페이지가 떨어져 있어도 무관(**연속성 불필요**).
  - **NeoStudio2**: **book 단위 관리** → book에만 종속되면 page는 떨어져도 무관.
  - **외부 업체 제공**: 해당 업체 개발물이 **떨어진 코드를 읽을 수 있는지**에 따라 발급 방식이 달라짐.

**개발 반영**
- 자동 할당 기본 = **연속 부족 → book 새로 분리**, book 내부 조각 병합 금지. (엔진 `allocationEngine.ts` 이미 구현)
- **추가 필요**: 서비스별 `pageContiguityRequired` 플래그 → CasterN 등 연속 불필요 서비스는 조각 page 활용 허용(효율↑), NeoStudio2는 book 종속 기본.

## 2. 고객 등급(Grade)별 할당 범위의 의미 (확인2)

**판단: 의미 있음** — "사용량 규모"에 근거.
- 폼솔루션 사용량, 편집툴(책 편집–출판사) 사용량을 대략 파악해 범위 산정.
- Owner 코드는 **고객사마다 다름**, **프로젝트마다 Owner 별도 발급이 원칙**.
- 단, **물량 작은 프로젝트는 내부적으로 NeoStudio2의 Owner 하위 book 할당으로 흡수**.
- **폼솔루션은 Owner 코드를 따로 생성해 운영**.

**정리(이원 운영)**: 대형/일반 프로젝트 = **Owner 별도 발급** · 소규모 = **NeoStudio2 Owner 하위 book으로 흡수**.

## 3. 자동 할당 대상 Owner & 등급별 SO 설계 (확인3)

- **대상 Owner 코드는 고정**하되, **등급마다 SO(Section–Owner)를 다르게** 할당.
- **G / N 구분 필요.**

**등급별 예시 설계**

| 등급 | 할당 규모 | SO 설정 |
|------|-----------|---------|
| a | 1,000 페이지 | SO – S 0 |
| b | 100 페이지 | SO – S 3 |

- **개발 요건**: 폼솔루션 개발 시, 할당 코드를 **등급별로 S를 둘 다 가질 수 있도록** 개발. page 규모에 따라 사용할 **OBP 배정**. → *개발팀 확인 필요.*

**"사전 예약"의 의미**
- 용도: **B2B용 / 대표님 연구용 / 소리펜 고객사용**.
- 특히 **소리펜과 팝펜이 혼용되지 않길 원하는 고객사**에 **사전 확보**하여 제공.
- **펜 혼용 관리**: 소리펜·필기펜이 **동일 SOBP**를 써도 **Ncp/Ndp로 다르게 관리**되므로 동일 page 사용 가능, 단 **구분 관리가 원칙**.

## 4. 고객별 코드 종류(N/G) 할당 정책 (확인4)

**사례**
- 교원 + 구몬: **N, G 모두** 사용(소리펜·필기펜 함께).
- 소리펜 중심 고객: 주로 **G코드**.
- NeoStudio2: X노트(코디언 등) 다른 고객사라도 **우리(Neo) 코드 할당**.
- 신규 서비스: **G/N 선택은 Neo가 정함.**

**코드 종류 할당 기준**

| 구분 | 할당 코드 |
|------|-----------|
| 해외 | N 코드 (원문 N/S이나 **S코드 제외 결정**) |
| 국내 – 소리펜 | G 코드 |
| 국내 – 소리 + 필기 | N 코드 |

> 주의: **편집 신규 할당은 편집 파트를 끼고 진행**하는 것이 안전.
> **결정(2026-07-15): S코드는 NcodeCenter 범위 제외** — 취급 코드 종류는 **N/G** 두 가지.

## 5. Section / Owner 공유 가능 여부 (확인5)

**답: 공유 불가.**
- **Section / Owner 는 공유하지 않는다.** 프로젝트(고객사)는 **SO로 구분**해 관리.
- book을 달리해 쓰는 것 자체는 가능하나 **관리가 어려워지므로 지양**.
- **빈 공간이 남더라도 다른 프로젝트가 같은 SO를 재활용하지 않는다.**

> 참고: 앞서 데이터에서 발견한 **공유 owner(S5/O100 등)** 는 이 원칙상 **지양 대상**(내부 재사용/명명 이슈일 가능성). 대시보드에선 정보로 표기하되, 신규 발급은 SO 미공유 원칙을 따른다.

## 6. 공통(커먼)코드 · 고객사 계층 · 사용 서비스 · 티켓 (프로토타입 반영, 2026-07~08)

> 프로토타입에서 raw 데이터(NSP/NWP 엑셀·커먼 시트)를 정리하며 확정한 정책. 상세 근거는 §0 Changelog PC-006~PC-017.

### 6.1 공통코드 중앙 모델 (PC-006~009)
- **코드 정본 = `(타입 k, Section, Owner)`** 중앙 레지스트리(`commonCodes.ts`). 옛 `nspCommon/nwpCommon` 불리언 플래그 폐기.
- 타입 **k = N(PDS3) · G(PDS2) · A(IDS, 이력전용 historyOnly)**. A는 코드 할당·편집 없이 검색/이력만.
- **홀더 회사 1개 = 코드 1개**로 분리: 네오노트-27 → 네오노트-0-27 / 3-27 / 14-27 / IDS-27. 회사·프로젝트·편집·소유권이 모두 코드 단위로 일관.
- **커먼코드 판정·필터는 레지스트리 기준.** 사용 고객사가 없는 코드(예: 팝펜스티커-26)는 공유코드로 보지 않음.

### 6.2 고객사 계층 = 상위 / 하위 / 단독 (PC-013~015)
- **상위(대표) 고객사** = 공통코드를 **보유**한 대장.
- **하위 고객사** = 공통코드를 **사용**(멤버십 귀속)하는 고객사. **정식 회사 레코드**로 관리 — 담당자·사업자·주소 등 상세를 갖고, 목록에서 이름순으로 섞여 노출·검색되며, 클릭 시 회사 상세가 열린다. **하위의 SOBP/코드 내역은 코드 프로젝트·SOBP 맵에서 관리**(고객사 상세에는 코드를 넣지 않음).
- **단독 고객사** = 공통코드와 무관한 일반 고객사.
- 대표(상위) 회사는 **자기 코드의 하위가 될 수 없다** → 수정 폼에서 자기 코드 비활성화.
- 사용 고객사(cu)는 별도 회사가 없더라도 빌드가 **최소 정보 회사 레코드를 생성**해 계층에 편입(정식 고객사화).

### 6.3 사용 서비스 (PC-010~012)
- 항목 = **casterN(편집툴) · 아이글 · 폼솔루션 · NeoStudio2 · 서비스없음(코드만 발급)**. (구 "네오노트" → **NeoStudio2** 리네임.)
- **서비스 지정은 SOBP 맵의 [직접 코드 할당]에서만** 한다(발급 지점에서 용도 지정 = 중앙집중).
- **편집 데이터로 만들어진 코드 = casterN**(자동). **[편집 프로젝트] 메뉴 = casterN 서비스 관리** 화면.
- **[코드 프로젝트]는 조회·검색 전용**(업체·서비스별). 프로젝트 등록 기능 없음.
- 외부에 코드만 발급(서비스없음)하면 사용량 모니터링 불가, 자체 서비스는 모니터링 대상.

### 6.4 티켓 발급 (PC-016)
- **N Key** = 물리 키(오프라인 편집툴, 계정 불필요). **App Key** = 계정과 연동되는 키(온라인·SDK). 좌측 메뉴로 구성.
- **정산(과금)** = 유료 / 무료 / 체험 / 미정. 발급 목록에서 티켓별 등록.
- 출처는 **대장(ledger, 과거 발급 이력) vs 신규발급**으로 구분.

### 6.5 예외·운영 제약
- **미할당 코드 예외(PC 참조)**: 편집 서비스가 미할당 코드도 쓰던 시기의 S3/O12(901플래너 스프링) — **코드는 네오노트12 소유(코드발급), 편집 실적은 네오노트-1012 귀속**. 향후 미할당 코드 사용 차단 예정.
- **프로젝트 종료 고객사**(closed) = 코드 발급 이력만 보관.
- **원본 Excel 편집 금지(PC-017)**: NWP/NSP 엑셀은 도형·이미지를 포함하므로 프로그램으로 저장 금지. 정책/데이터 변경은 **사용자가 Excel에서 직접 수정** 후 재빌드.

## 7. SOBP 실시간 발급 (NDP 연동) — Ncode 프린터

> 근거: 프린터 드라이버 SOBP 할당 설계(2026-08 수령). 상세 = [SOBP 할당 (NDP 연동) 참조](NcodeCenter-SOBP-Allocation.md). ※ 별도 앱 화면 없음 — 문서로만 관리.
> 상태: **인증 체인 ✅ 구현 완료 / 발급 API `/ncode/issue` 📋 설계 확정·스펙 미정.**

### 7.1 할당 경로 2가지 (배타 아님)

| 경로 | 주체 | 단위 | 상태 |
|---|---|---|---|
| **A. 관리자 할당** | 내부 직원 — `[SOBP 맵] ▸ 직접 코드 할당` | S/O/B/P **블록** | ✅ 구현 |
| **B. 실시간 서버 발급** | 서비스 클라이언트 — NDP `/ncode/issue` | **페이지** | 📋 스펙 미정 |

기본 구성 = **관리자가 A로 코드 풀(블록)을 잡아 주고, 클라이언트는 그 안에서 B로 소비**한다.

### 7.2 원칙

1. **서버 중심 할당** — 클라이언트가 SOBP를 임의 생성하지 않는다(고객사·기기 간 충돌 방지). 기존 **무겹침·SO 공유 불가** 원칙과 같은 근거.
2. **Owner = 고객사(리소스오너) 전용** — 고보안 고객은 전용 Section/Owner 범위.
3. **Book = 문서 1건(원본 버전과 1:1)** — 원본이 바뀌면 새 Book. **Page 1..N 연속 배정**(§1 연속성 원칙과 동일).
4. **등록 전 인쇄 금지** — 배경 문서 등록이 끝나기 전에는 실제 인쇄를 진행하지 않는다(미등록 Ncode 종이 = 필기 매칭 불가).
5. **재사용 금지 기본** — 원본 해시·페이지 수·크기·방향·배율이 모두 같을 때만 재사용 가능. 검토자별 출력은 검토자마다 별도 SOBP.
6. **오프라인 사전 확보 블록** — 오프라인 대비로 블록을 미리 받아 둘 수 있으나, **NcodeCenter 원장에는 '할당됨(발급)'** 으로 기록한다(예약 상태 없음 — PC-004·PC-005).
7. **용도 식별** — 이 경로로 나가는 코드는 사용 서비스 **`Ncode 프린터 (드라이버)`** 로 지정한다(PC-019).

### 7.3 실패 게이트

| 실패 지점 | 정책 |
|---|---|
| 토큰 무효 | silent refresh → 실패 시 재로그인 유도(발급 진행 안 함) |
| SOBP 발급 실패 | **인쇄 중단.** 재시도 / 관리자 코드 재고(잔여 블록) 확인 |
| 배경 문서 등록 실패 | **인쇄 중단(기본).** |
| 실프린터 출력 실패 | 등록 유지 — **같은 SOBP로 재인쇄** |
| 발급 후 미사용 SOBP | 회수(반납) 정책 **미정** → 협의 항목 |

### 7.4 미결 (협의 필요)

- `/ncode/issue` **엔드포인트 스펙**(요청/응답·블록 크기·재시도) 확정 — 개발팀
- **미사용 SOBP 회수(반납)** 정책 — 발급됐으나 인쇄되지 않은 코드의 처리
- 실시간 발급 결과의 **NcodeCenter 원장 동기화 주기·방식**(이벤트 `sobp.allocated` 수신 vs 배치)
- Ncode 프린터 전용 **Section/Owner 풀 배정 기준**(고객사별 전용 Owner 원칙 적용 범위)

## 핵심 원칙 요약

1. **무겹침**: 신규 할당은 기존과 절대 겹치지 않는다.
2. **연속성은 book 단위**: 연속 부족 시 book 분리, book 내 page 연속 유지(조각 병합 금지). 연속성 요건은 **서비스별 상이**(CasterN 불필요, NeoStudio2 book 종속).
3. **SO = 프로젝트/고객사 식별 축**: Section·Owner는 **프로젝트 간 공유 불가**.
4. **Owner 발급 이원화**: 프로젝트 단위 별도 발급 원칙, 소규모는 NeoStudio2 Owner 하위 book으로 흡수. 폼솔루션은 별도 Owner 운영.
5. **등급별 SO 차등**: 등급마다 S를 다르게(예: a=S0/1000p, b=S3/100p), G·N 구분.
6. **코드 종류 규칙**: 해외 N · 국내 소리펜 G · 국내 소리+필기 N. 최종 선택은 Neo 결정. (**S코드 제외**, N/G만)
7. **펜 혼용 관리**: 동일 SOBP라도 Ncp/Ndp로 분리 관리 가능(구분 관리 원칙).
8. **실시간 발급도 서버 중심**: 클라이언트 임의 생성 금지, 배경 등록 전 인쇄 금지, 재사용 금지 기본(§7).
