## 1. 기능 개요

**이 화면의 계정 = 티켓 고객사에 App Key 를 발급하기 위한 키 발급 계정**이다 `PC-128`. 이 화면은 등록된 **키 발급 계정의 목록**이며, 여기서 계정을 **추가·상세 확인·삭제**한다. 등록과 상세 수정은 `TKT-02`에서 한다.

| 항목 | 내용 |
|---|---|
| 권한 | STAFF / ADMIN |
| 진입 | 좌측 메뉴 **[티켓 발급] ▸ [App Key 관리 (계정 발급)]** (`/tickets/account`) |
| 형제 화면 | `TKT-03` N Key 관리 |
| 하위 화면 | `TKT-02` 계정 등록(`/tickets/account/new`) · 상세·수정(`/tickets/account/{email}`) — 탭은 **계정 정보 · App Key 발급** 2개 `PC-131` |
| 고객사 | **티켓 고객사** — nkey(HLP) 대장(`db/source/nkey(HLP).xlsx`)의 프로젝트명 17곳 + 티켓 화면에서 **[＋ 신규 등록]**한 고객사. 고객사 관리(`MEM-01`)의 회사와 **별개**다 `PC-123` |
| 발급 범위 | S/O/B 범위는 **nkey 대장 이력**과 SOBP 맵에서 **(K)** 로 표시된 할당에서 고른다. 고객사 관리의 SOBP 할당을 쓰지 않는다 `PC-123` |

> **계정 수는 제한이 없다.** 한 고객사에 담당자별로 여러 계정을 둔다 `PC-029`. ID(email)만 전체에서 유일하면 된다.
> **App Key 발급은 선택이다.** 계정만 먼저 등록해 두고 키는 나중에 `TKT-02` 상세에서 붙일 수 있다.
> **서비스 계정은 여기서 다루지 않는다** `PC-128` `PC-131`. 서비스 로그인 계정과 CasterN 권한은 고객사 관리 상세(`MEM-02`)의 **계정 및 서비스 권한**에서 관리한다. 이 화면에는 인증 서비스·권한 항목이 없다.

## 2. 화면 흐름 (Flow)

```
좌측 메뉴 [티켓 발급] ▸ [App Key 관리 (계정 발급)]
   └─▶ TKT-01 키 발급 계정 목록
          ├─ [＋ 계정 추가] ─────▶ TKT-02 등록 (/tickets/account/new)
          │                          └─ [계정 추가] ─▶ 목록에 노출
          ├─ ID(email) · [상세] ─▶ TKT-02 상세·수정 (/tickets/account/{email})
          │                          ├─ 계정 정보 탭  [저장]   ─▶ 계정 정보 반영
          │                          └─ App Key 발급 탭        ─▶ LOG-01 기록
          └─ [삭제] ─(확인창)─▶ 계정 + 연동 App Key 삭제

  (서비스 계정·CasterN 권한 ─▶ MEM-02 고객사 상세 ▸ 계정 및 서비스 권한  PC-128)
```

## 4. 사용법

화면은 **요약 5칸 → 한 줄 필터 → 8열 표** 순서다.

> **초기 데이터** `PC-128` — 개발팀 대장(`db/source/Caster_계정_퍼미션_티켓.xlsx`)의 계정 15건(네오랩 등)은 **서비스 계정**이라 고객사 관리 상세(`MEM-02`)의 **계정 및 서비스 권한**으로 옮겨 갔다. 따라서 이 목록은 **빈 상태(S2)에서 시작**하고, 직원이 **[＋ 계정 추가]** 로 등록한 키 발급 계정만 나온다.

### 4.1 요약 (S1)

모든 칸은 **키 발급 계정** 기준으로 센다 `PC-128`.

| 칸 | 내용 |
|---|---|
| 등록 계정 | 키 발급 계정 수 |
| App Key 연동 | App Key가 **1개 이상** 있는 계정 수 |
| App Key 없음 | 아직 키가 없는 계정 수 (계정만 등록한 상태) |
| 발급 App Key | 발급된 키의 총 개수 |
| 티켓 고객사 | 키 발급 계정이 있는 **티켓 고객사 수**(중복 제외) `PC-123` |

> 요약은 **전체 기준**이며 필터의 영향을 받지 않는다.

### 4.2 필터 · 검색 (S3 · S4)

| 항목 | 규칙 |
|---|---|
| 고객사 | **고객사 전체** + 키 발급 계정이 있는 **티켓 고객사**만 목록에 나온다 `PC-123` |
| 검색 | **ID(email) · 이름 · 고객사** 를 함께 본다 |
| 건수 | 필터 결과 건수를 함께 표시 |

두 조건은 **동시에** 걸린다. 조건에 맞는 계정이 없으면 **조건에 맞는 계정이 없습니다.** (S4)

> 인증 서비스 필터는 없다 `PC-131`.

### 4.3 목록 (S1)

| 열 | 표시 |
|---|---|
| 고객사 | **티켓 고객사** 이름 `PC-123` (고객사 관리 `MEM-01` 의 회사가 아님) |
| ID (EMAIL) | 계정 ID. 누르면 `TKT-02` 상세로 이동 |
| 이름 | NAME(담당자명) · 없으면 `—` |
| App Key | **발급된 키 값을 그대로 보여준다** `PC-067` (영문·숫자 29자 `PC-066`). 없으면 **미발급** |
| 코드 범위 | 그 키에 물린 **S/O/B 범위 수** — 범위는 nkey 대장 이력 · SOBP 맵 **(K)** 할당에서 고른다 `PC-123`. 툴팁에 범위 전체. 누르면 **App Key 발급** 탭 |
| 사용기간 | **코드 범위(=티켓)별 기간** `PC-118` — 첫 티켓의 **시작 ~ 끝**(무제한), 티켓이 여럿이면 `… 외 N`. 없으면 `—`. (계정 속성이 아님 — 발급은 `TKT-02` App Key 발급 탭) |
| 등록일 | 계정 생성일 |
| (작업) | **[상세]** · **[삭제]** |

> 인증 서비스 열 · CasterN 권한 표시는 **삭제**되었다 `PC-131`. 서비스 권한은 `MEM-02` **계정 및 서비스 권한**에서 본다.

**셀을 누르면 그 항목의 탭으로 바로 간다** `PC-067` — 상세에 들어가서 탭을 다시 찾지 않게 하기 위해서다.

| 누른 셀 | 이동 |
|---|---|
| **App Key** · **코드 범위** | `TKT-02` ▸ **App Key 발급** 탭 |
| 그 밖의 셀(행) | `TKT-02` ▸ **계정 정보** 탭 |

### 4.4 계산 규칙

**(가) 요약 — 키 발급 계정 기준**

```
등록 계정    = 키 발급 계정 수
App Key 연동 = 키가 1개 이상인 계정 수
App Key 없음 = 등록 계정 − App Key 연동
발급 App Key = 모든 계정의 키 개수 합
티켓 고객사  = 계정의 고객사 이름 중복 제외 개수

예) InformDS 계정 1(키 1) · KODION 계정 1(키 1) · hyssos 계정 1(키 0)
    → 등록 3 · 연동 2 · 없음 1 · 발급 2 · 티켓 고객사 3
```

### 4.5 계정 추가 (S1 → `TKT-02`)

**[＋ 계정 추가]** 를 누르면 `TKT-02` 등록 화면이 열린다. 등록을 마치면 **목록으로 돌아오고 새 계정이 표에 나타난다**.

### 4.6 삭제 (S5)

**[삭제]** → 확인창 → 계정과 **연동된 App Key가 함께** 삭제된다. 개별 App Key만 지울 때는 `TKT-02` 상세의 **[키 삭제]** 를 쓴다.

- [ ] **비밀번호 전달 방식** — 현재 화면 표시·복사. 메일 발송 등 안전한 전달 경로 필요 여부
- [ ] **키 회수(폐기)** — 삭제 외에 "정지/만료 처리" 상태가 필요한지
- [ ] 계정 1개에 App Key 여러 개를 허용하는 현재 방식의 **상한** 필요 여부 (고객사당 **계정 수**는 제한 없음으로 확정 `PC-029`)
- [ ] 서비스 측 **App Key 조회 방식** — 서비스가 키 발급 계정·App Key를 조회하는 API 규격 (개발팀 협의). 인증·권한 연동은 서비스 계정(`MEM-02`) 쪽 과제 `PC-128`
