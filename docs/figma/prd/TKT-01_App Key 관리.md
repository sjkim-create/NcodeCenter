## 2. 화면 구성

### 개요

App Key 를 발급하는 화면이다. 「**고객사 · App Key 계정 · 계정 상세**」 3단 한 화면이며 옛 `TKT-01` 계정 발급(목록)과 옛 `TKT-02` 계정 등록·수정을 합쳤다 `PC-146` `PC-158`. 고객사는 **고객사 관리 고객사를 불러온다**(여기서 등록하지 않음) `PC-153`. 계정은 **App Key 계정** — 계정과 App Key 가 매칭되는 개념으로, 고객사 관리의 **서비스 계정**(서비스 권한)과 별개다. 화면 모양은 `TKT-02` N Key 관리와 같은 조각을 쓴다 `PC-154`. **App Key 와 티켓은 다른 개념** — 계정 상세의 탭이 [티켓 내역] · [티켓 발급] · [정산] · [계정 정보] · [권한] 순서다 `PC-208` `PC-211`. App Key 는 계정을 만들 때 자동 생성되고(1계정 1키) [계정 정보]에 보인다 `PC-210`.

### 기능 개요

**App Key 를 발급하는 화면**이다. 「**고객사 | App Key 계정 | 계정 상세**」 3단 한 화면에서 고객사를 고르고, 그 고객사의 App Key 계정을 만들고, 계정마다 App Key 와 코드 범위(=티켓)를 발급한다.

**App Key 의 용도** `PC-245` — **Ncode SDK** 를 쓰는 고객사와 **Caster U** 를 쓰는 고객에게 준다. Caster U 는 **계정이 필요**하다 — 계정을 만들면 App Key 가 생기고, [권한] 탭에서 **Caster U 권한**을 설정해 두면 그 계정 · App Key 로 Caster U 를 쓸 수 있다.

| 티켓 | 쓰는 곳 · 쓰는 사람 | 계정 | 발급 · 지정 화면 |
|---|---|---|---|
| **App Key** (계정 소속 티켓) | **Ncode SDK** 를 쓰는 고객사 · **Caster U** 를 쓰는 고객 — App Key 에 **권한(Caster U 권한 20항목)** 을 설정해 발급하면 그 계정으로 Caster U 를 쓸 수 있다 | **필요** — 계정을 만들면 App Key 자동 생성(1계정 1키) · 티켓은 계정마다 여러 개 | `TKT-01` App Key 관리 |
| **N Key** (.nkey 파일) | **Caster Lite**(오프라인 편집툴) 사용자 — 프로필 **LEGACY**. **CasterN 을 오프라인으로 쓰는 경우**에는 프로필 **HYBRID** + CasterN 권한 6개로 발급 | 필요 없음(파일 키) | `TKT-02` N Key 관리 |
| **서비스 티켓** | **casterN · 폼솔루션** 서비스(온라인) 사용 고객사 — 사용자에게 주는 키가 아니라 고객사 계정과 매칭해 서비스 사용을 승인하는 기준(§6.6) | 고객사의 서비스 계정과 매칭 | `MEM-02` 고객사 관리 ▸ 서비스 티켓 |

| 항목 | 내용 |
|---|---|
| 권한 | STAFF / ADMIN |
| 진입 | 좌측 메뉴 **[티켓 발급] ▸ [App Key 관리 (계정 발급)]** (`/tickets/account`) |
| 고객사 | **고객사 관리(`MEM-01`) 고객사를 불러온다** — 여기서 고객사를 등록하지 않는다 `PC-153` |
| 계정 | **App Key 계정** — 계정과 App Key 가 매칭되는 개념(계정당 App Key 1개) |
| 과거 자료 | 개발팀 **Caster_계정_퍼미션_티켓.xlsx** 의 계정 15건(대장) — 고객사명으로 고객사 관리 고객사에 잇는다 |
| 짝 화면 | `TKT-02` N Key 관리 — 같은 3단 · 같은 UI 조각 `PC-154` |

> **App Key 계정 ≠ 서비스 계정.** App Key 계정은 *계정과 App Key 를 매칭*하는 발급 단위이고, 고객사 관리(`MEM-02`)의 **서비스 계정**은 *고객사가 서비스 권한(CasterN 등)을 갖게 하는* 계정이다. 두 계정은 서로의 목록에 나오지 않는다 `PC-128` `PC-153`.

### 화면 흐름 (Flow)

```
좌측 메뉴 [티켓 발급] ▸ [App Key 관리 (계정 발급)]
   └─▶ TKT-01  ┌ 고객사(고객사 관리) ┬ App Key 계정 ─────┬ 계정 상세 ─────────────────┐
               │ [발급 고객사]/[전체] │ 카드 목록          │ 탭: 계정 정보 / App Key 발급 │
               │ 검색 · 고객사 미연결 │ [＋ 계정 추가]      │                            │
               └──────────────────┴──────────────────┴────────────────────────────┘
      고객사 클릭 ─▶ 그 고객사 계정 · 첫 계정 상세
      [＋ 계정 추가] ─▶ 「새 계정 · 작성 중」 + 빈 폼 ─ [계정 추가] ─▶ 그 계정 상세 (범위를 골랐으면 App Key 동시 발급)
      계정 상세 ├ 계정 정보 [저장]
                ├ App Key 발급 ─ [코드 범위 발급] ─▶ 티켓 + 원장 티켓(TKT-02 목록에는 N Key 만) · LOG-01
                ├ 발급 내역 [티켓 수정] ─▶ 수정 폼 ─ [수정 저장] (티켓 · 키 삭제 없음 `PC-192`) · 티켓 선택 ─▶ Key 정보
                └ [계정 삭제] ─(확인창)─▶ 다음 계정 — 발급된 티켓이 있으면 비활성
      발급 범위 없음 ─▶ SOB-02 에서 SOBP 할당 후 다시
```

| `PC-118` 사용기간 | 계정이 아니라 **코드 범위(=티켓)마다** 유지 |
| `PC-119` 원장 티켓 | 코드 범위를 발급할 때마다 원장에 APP 티켓 1건. [티켓 수정] 시 함께 고친다 `PC-192` |
| `PC-200` 발급 내역 탭 | 계정 상세의 **첫 탭 [발급 내역]** — 지금까지 발급한 티켓(코드 범위)을 줄마다 **코드 구간(종류 · S · O · B · P)** 과 **발급일(대장분은 「대장」) · 권수 · 사용기간**, 정산, [수정] 으로 보인다. 줄을 누르면 그 아래에 Key 정보가 열리고 다시 누르면 접힌다. 발급분이 있으면 이 탭이 먼저 열리고(없으면 [App Key 발급]), [App Key 발급] 탭에는 발급 · 수정 폼만 둔다. 탭 순서 발급 내역 · App Key 발급 · 정산 · 계정 정보, 계정 저장 · 삭제 버튼은 [계정 정보] 탭에서만 |
| `PC-199` 하위 고객사 두 길 | 하위 고객사는 **상위 고객사 묶음 안에서도, 전체 목록 제자리에서도** 고를 수 있다. 하위 고객사를 바로 고르면 그 하위 고객사가 들어간 **모든 상위 고객사의 SOBP** 가 발급 범위에 나오고, 범위마다 「상위 · 상위 고객사명」 을 보인다 |
| `PC-198` 상위 고객사 접기 · 펼치기 | 상위 고객사 줄의 **▶ 로 하위 고객사를 접고 편다**(기본 접힘, 이름 옆 「하위 n」). 하위 고객사는 **왼쪽 세로 안내선 안에 들여** 보인다(└ · 「하위」 표시 없앰). 검색 중이거나 고른 고객사가 하위면 저절로 펼친다. App Key 관리 · N Key 관리 고객사 칸은 같은 조각 · 같은 모양 — N Key 고객사 칸의 「미정 n」 표시는 없앴다 |
| `PC-196` 하위 고객사 선택 | 왼쪽 고객사 목록에서 **하위 고객사는 상위(공통코드 보유) 고객사 밑에 └ 「하위」로 들여** 보인다. 고르고 [＋ 계정 추가] → App Key 발급 범위에 상위 SOBP 가 나온다. [발급 고객사] 보기에도 하위 고객사가 발급받은 상위 고객사가 함께 나온다 |
| `PC-195` 하위 고객사 · 구간 현황 | **하위 고객사는 상위(공통코드 보유) 고객사의 SOBP 영역으로 발급**한다 — 하위끼리는 Book · Page 가 겹치지 않게(`PC-174`). 범위를 고르면 아래에 **구간 사용 현황**(이미 발급된 구간 · 빈 Book 구간 · 입력 구간 사용 가능 여부)이 보이고, 빈 구간을 누르면 Start Book 이 그 자리로 간다 |
| `PC-192` 삭제 없음 · 수정 | 발급된 **티켓 · 키는 지우지 않는다.** 티켓 정보를 고치고, 바꾼 코드 구간은 **같은 S/O 의 할당 범위 안 + 다른 발급분과 겹치지 않을 때**(자기 자신 제외)만 저장한다. 발급된 티켓이 있는 계정은 삭제할 수 없다 |
| `P-05` 무겹침 | 범위는 **발급 범위 목록에서 고른다**(좌표를 타이핑하지 않음). Book · Page 만 지정 |
| `PC-174` SOBP 무겹침 | **N Key · App Key · 서비스 티켓은 SOBP 가 절대 겹칠 수 없다** — 계정 추가(범위 선택 시) · App Key 발급 · 코드 범위 추가 때 전체 발급분과 비교해 겹치면 막는다 |
| `PC-154` UI 통일 | `TKT-02` 와 같은 조각 — 한쪽만 고치지 않는다 |

#### 4.4 App Key 발급 · 티켓 발급 `PC-208`

**App Key** — 계정을 만들 때 **자동 생성**(1계정 1키, 영문 소문자 · 숫자 29자 예 `32b019140790385d8cb6fa32d9b81`). [계정 정보]에 키 값 · [복사] · 생성일, 이전 정책으로 2개면 둘 다(S8) `PC-210`.

**티켓**([티켓 발급] 탭) — **App Key 를 먼저 발급한 계정에만**(없으면 S17). 아래 항목으로 발급한다.

| 항목 | 규칙 |
|---|---|
| 발급 범위 (Caster 대장 이력 · SOBP 할당) | 이 고객사의 Caster 대장 범위 + **고객사 관리에서 할당한 SOBP**. 고르면 Section·Owner·Book·Code Type 이 채워진다. 없으면 **이 고객사의 발급 범위가 없습니다.** (S10) |
| Start Book (시작 북코드) · Book 볼륨 (권) | 범위 안. **Book End = Start + 볼륨 − 1** `PC-050` |
| Start Page · Page 볼륨 | 계정마다 B·P 영역을 다르게 잡는다 `PC-059` |
| Ticket Name (티켓 이름) `PC-261` | 「티켓 속성」 맨 위 한 줄. **제안 이름을 placeholder 로** 보인다 — **.nkey 파일명과 같은 규칙**(파일로 전달되지 않는 **이름**일 뿐) `{고객사}_{S}s_{O}o_{Book 볼륨}b_{Page 볼륨}p_{발급일 YYYYMMDD}` — B · P 자리는 **Start Book · Start Page 가 아니라 볼륨** `PC-263`(고객사 = 고객사 관리 이름 · 못 쓰는 문자는 `_`). 예 Book 8~11(4권) · 512쪽 → `KODION-46_3s_46o_4b_512p_20261023`. 범위 · Book · Page 를 바꾸면 제안도 바뀐다. 처음엔 **연한 placeholder**, 칸을 눌렀다가 **입력 없이 벗어나면 제안 이름이 값으로 채워져 진하게** 보인다(그 뒤에도 범위 · Book · Page 를 따라 바뀜) `PC-262`. 고치기 시작하면 직접 쓴 이름으로 굳고, 다 지우고 벗어나면 다시 제안 이름. **비워 두면 제안 이름으로 발급**.
